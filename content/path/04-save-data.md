## 这一关你要做成什么

做完这一关，你的网页能做到三件事：用户用邮箱注册、登录；登录后写下的东西存在云端；换手机、换电脑登录，东西还在，而且别人看不到。

不是每个作品都要走到这一步。这一关的第一件事，是帮你判断「我到底需不需要」。不需要就别做，省下的时间留给后面几关。

过关标准：你用两个不同的邮箱各注册一个账号，A账号写的内容，B账号登录后看不到；用另一台设备登录A账号，内容还在。

## 先懂一件事

### 数据可以放在两个地方

放在用户自己的浏览器里，或者放在云端的[数据库](/words/database)里。

浏览器里的存储叫[localStorage](/words/localstorage)，像每个人随身带的小本子。好处是不用注册、不用服务器、不花钱。坏处也明显：小本子只在这一部手机的这一个浏览器里。换设备看不到，清理浏览器数据就没了，你自己也看不到用户写了什么。

云端数据库像一间公共档案室，每份档案贴着主人的名字，用户凭账号去取。换设备能取，你也能统计。代价是你要多管三样东西：登录、权限、密钥。

### 什么时候根本不需要数据库

下面这些情况，localStorage就够了：

- 只给你自己用的小工具，比如习惯打卡、记账本、倒计时。
- 数据丢了不心疼，或者可以导出备份。
- 不需要换设备同步，不需要多人共享。
- 你还在验证「有没有人要用」，不想先花一个周末搭登录。

下面这些情况，才需要数据库：

- 用户要在手机和电脑之间同步。
- 多个用户之间要共享或互相看到（评论、排行榜、预约）。
- 你要收集用户提交的东西（表单、报名、反馈）。
- 后面要收钱：付了钱的人是谁、权益到哪一天，必须记在云端。

一个粗暴但有用的判断：如果你的产品里出现「我的」两个字，比如「我的收藏」「我的订单」，大概率需要。

### 钥匙分两种，这是本关最重要的安全知识

Supabase给你的钥匙，按官方文档（2026年11月）现在叫这两种名字：

| 名字 | 样子 | 能放前端吗 | 权限 |
|---|---|---|---|
| Publishable key（可公开密钥） | `sb_publishable_`开头 | 可以 | 低，只能做行级安全策略允许的事 |
| Secret key（秘密密钥） | `sb_secret_`开头 | 绝对不行，只能放服务端 | 高，会绕过行级安全策略 |

老教程和旧项目里你会看到另一套名字：`anon`和`service_role`，是以`eyJ`开头的一长串。它们分别对应「可公开」和「秘密」两种角色。官方说明计划在2026年底前淘汰旧的这一套（到2027年1月以后请回官方API Keys页确认现状），旧Key在你手动停用之前仍然有效。所以：新项目用`sb_publishable_`和`sb_secret_`；看到教程让你复制`eyJ`开头的长串，说明它针对旧版。

记住一个对应关系：publishable对应anon，secret对应service_role。

为什么publishable可以公开？因为它只是一张「访客证」。真正决定访客能看什么的，是你在每张表上设置的[行级安全策略](/fix/supabase-rls)（RLS）。没配RLS，访客证也可能把整张表读走。所以「publishable可以公开」这句话，有一个前提：每张表都开了RLS并写了策略。

secret是万能钥匙。它出现在浏览器里，等于数据库大门敞开。Supabase会检查请求来源，在浏览器里用它会被拒绝（HTTP 401），但你不要把这当成保险，正确做法是它压根不出现在前端代码里。

### 环境变量：钥匙放哪儿

[环境变量](/words/env-var)是放在代码外面的配置。本地开发时写在项目根目录的`.env.local`文件里，上线时填在Vercel后台。这个文件必须被`.gitignore`忽略，否则一次`git push`就把钥匙公开到GitHub了，处理办法见[密钥泄露急救](/fix/secret-leaked)。

Next.js有一条规则：变量名以`NEXT_PUBLIC_`开头的，会被打包进浏览器代码，所有访问者都看得见；不带这个前缀的只在服务端存在。所以：

- 项目地址和publishable key，可以带`NEXT_PUBLIC_`前缀。官方快速入门用的变量名是`NEXT_PUBLIC_SUPABASE_URL`和`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`。
- secret key绝不能带这个前缀。

## 动手

### 第0步：看一眼国内访问的现实

Supabase是海外服务。Supabase官方没有声明在中国大陆的访问质量。部分地区、部分网络下访问可能不稳定，请自测：用你自己的手机4G和家里宽带，各打开一次你项目的网址，各注册一次。

如果测下来不稳定，你有这几条思路：

- 你的用户主要在海外，或者只是做作品集：继续用Supabase。
- 你的用户主要在国内：换国内的后端服务。腾讯云的「云开发CloudBase」是一个选项，官方文档（docs.cloudbase.net）介绍它提供数据库、云函数、身份认证和静态托管，控制台在tcb.cloud.tencent.com。免费或体验额度以腾讯云官方价格文档为准。
- 其他国内云厂商也有类似的「后端一体化」产品，名称和收费请自己去官网核实。

本关后面的流程以Supabase为例。如果你换了CloudBase，把提示词里的「Supabase」换成它，并加上一句「请先读docs.cloudbase.net的官方文档再动手」，思路是一样的：建表、配权限、前端用公开的配置、秘密的东西放服务端。

### 第1步：先判断，再决定

把你的作品拿出来问自己三个问题：用户要换设备吗？用户之间要互相看到吗？数据丢了会出事吗？三个都是「不要」，用localStorage。

如果你要走localStorage这条路，复制这条提示词：

```prompt 复制给Claude Code或TRAE
我的网页需要把用户输入的数据保存在浏览器里，刷新页面后还在。请用localStorage实现。
要求：
1. 先用三句话告诉我你打算存什么、用什么名字存、数据长什么样，等我说「继续」再动手。
2. 读取数据时要处理「没有数据」和「数据坏了」两种情况，不能让页面白屏。
3. 加一个「导出备份」和「导入备份」按钮，数据以JSON文件的形式导出，因为localStorage清理浏览器就没了。
4. 完成后，教我怎么在浏览器的开发者工具里看到存进去的数据，并告诉我这些数据换一个浏览器为什么看不到。
```

你会看到：AI先回三句话的计划，等你确认。确认后页面刷新数据还在，页面上多了导出和导入按钮。

如果看到别的：刷新后数据没了，多半是代码没读取，或者你用了无痕模式。把现象原样告诉AI，并加一句「请先说明原因再改」。页面空白见[页面白屏](/fix/blank-page)。

做完这一步，如果你的作品确实不需要云端，可以跳到[第5关](/start/add-ai)。注意第5关的「每人每天几次」依赖这一关的登录和数据库，跳过的话，第5关里有不用登录的替代方案（访问口令加全站总次数上限）。需要云端，继续往下。

### 第2步：确认项目形态

本关需要一个有「服务端」的项目，推荐Next.js（[Next.js词条](/words/nextjs)）。如果你第2关做的是单个HTML文件，让AI先帮你迁移。

```prompt 复制给Claude Code或TRAE
请先阅读当前项目，告诉我：
1. 现在是什么类型的项目（单个HTML、Vite、Next.js还是别的），用了哪些文件。
2. 我接下来要加「邮箱注册登录 +云端保存数据」，需要有一个能放服务端代码的结构。你建议保持现状还是迁移到Next.js？各自对我的影响是什么。
3. 如果要迁移，列出会改动哪些文件，原来的功能和样式怎么保证不丢。
只做分析，不要改任何文件。我选定方案后你再动手。
```

你会看到：AI用大白话描述项目现状，给出建议和风险。没有改任何文件。

如果看到别的：AI直接开始改文件了，按Esc停下，然后说「我说了只分析，请回退刚才的改动」。回退方法见[撤销AI的改动](/fix/undo-ai-changes)。

确认迁移前，先执行一次存档。

```bash
git add -A
git commit -m "迁移前存档"
```

### 第3步：在Supabase后台新建项目（你自己点）

去supabase.com注册并登录，在Dashboard里新建一个项目。按钮文案、选项以界面为准，大致会让你填项目名、数据库密码和服务器区域。

- 数据库密码用密码管理器保存，不要发给AI，不要写进代码。
- 区域选离你用户近的。国内用户可以先选亚太地区的，实际速度请自测。

免费档的限制（来自官方定价页，2026年11月）：最多2个活跃项目，数据库500MB，每月5万活跃用户，1GB文件存储。项目闲置1周会被暂停。暂停不会删数据，但网站会连不上，你要回后台手动恢复。做作品集时要特别注意这一条，第7关会再提。

你会看到：项目创建需要一两分钟，完成后进入项目首页。

如果看到别的：创建一直转圈，换网络试一次；多次失败就按第0步的思路考虑国内方案。

### 第4步：拿到两个值，放进.env.local

在项目页面点Connect，会看到项目地址（URL）和publishable key。官方快速入门说明Key从这个面板拿。在Settings的API Keys页面可以看到全部密钥，包括secret key（官方文档写的路径是Settings > API Keys）。

这一步只拿两个：项目地址和以`sb_publishable_`开头的Key。secret key先不要碰。

```prompt 复制给Claude Code或TRAE
我要把Supabase接到这个项目里。先不要写业务代码，只做配置准备：
1. 创建.env.local文件，里面放两个变量：NEXT_PUBLIC_SUPABASE_URL和NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY，值先留空，我自己填。
2. 检查.gitignore，确认.env.local被忽略；如果没有，加上。然后运行`git status`，证明.env.local不会被提交。
3. 同时创建一个.env.example，只写变量名不写值，方便以后看。
4. 安装官方包@supabase/supabase-js和@supabase/ssr。安装前先去Supabase官方文档（supabase.com/docs里Next.js的快速入门）确认当前推荐的写法。
完成后停下来，告诉我下一步我该做什么。注意：不要让我把任何密钥贴到对话里。
```

你会看到：项目里多了`.env.local`和`.env.example`，AI运行`git status`后的输出里没有`.env.local`。

然后你自己打开`.env.local`，把两个值填进去。填完保存。

如果看到别的：`git status`里出现了`.env.local`，说明没被忽略，让AI修好再继续，千万不要先提交。

### 第5步：建表，并开启RLS

行级安全策略（RLS）是这一关的核心。官方文档的说明是：开启RLS后，在你创建策略之前，用publishable key不能通过API访问任何数据。官方还提醒：建表后要手动开启RLS并检查权限授予，不要假设它默认就是开着的。

我们做一个最小的「笔记」表：每条笔记属于一个用户，用户只能看、改、删自己的。

```prompt 复制给Claude Code或TRAE
请为「笔记」功能设计Supabase数据库，先只写方案，不要执行。
上下文：每个登录用户可以创建、查看、修改、删除自己的笔记，看不到别人的。
请给出：
1. notes表的字段（id、user_id指向登录用户、内容、创建时间），说明每个字段为什么要有。
2. 一份可以直接粘贴到Supabase后台SQL Editor里运行的SQL：建表、开启RLS、给authenticated角色授予必要权限、为select/insert/update/delete各写一条策略，条件是登录用户的id等于user_id（用auth.uid()）。查Supabase官方RLS文档确认写法，并建议用(select auth.uid())的形式。
3. 逐条解释这份SQL做了什么，让一个不会写SQL的人也能看懂。
4. 明确告诉我：这份SQL有没有可能让未登录的人读到数据。
验收标准：每张表都必须开RLS，没有任何策略是「允许所有人」。
```

你会看到：AI给出一段SQL和逐条解释。你不用背，但要找到几个关键词：`enable row level security`，以及`auth.uid()`出现在每条策略里。

把SQL复制到Supabase后台的SQL Editor，运行。

你会看到：运行成功的提示。去Table Editor能看到`notes`表，且表上显示已启用RLS（具体标识以界面为准）。

如果看到别的：运行报错，把报错原文整段贴给AI，说「这是Supabase SQL Editor运行你给的SQL时的报错，请修正后给我完整的新版本」。报错信息不含密钥，可以贴。RLS相关的常见问题见[RLS拦住了请求](/fix/supabase-rls)。

### 第6步：做登录和读写

这一步是写业务代码，让AI先说计划。

```prompt 复制给Claude Code或TRAE
请在这个Next.js项目里实现：邮箱+密码注册登录，登录后可以增加、查看、删除自己的笔记。
先说计划，等我确认再动手。计划要包含：要新建或修改哪些文件、登录状态怎么保存、页面有哪几个。
约束：
1. 只使用环境变量里的NEXT_PUBLIC_SUPABASE_URL和NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY。不要使用、不要提及secret key，前端代码里不允许出现任何以sb_secret_开头或叫service_role的内容。
2. 按Supabase官方Next.js文档的推荐方式处理登录状态。
3. 所有读写都通过supabase-js，并依赖RLS做权限，不要自己在前端「过滤掉别人的数据」当作安全措施。
4. 界面保持现有风格，注册、登录、登出、笔记列表各一个清楚的状态：加载中、失败、成功。
验收标准：我能注册、登录、写一条笔记、刷新后还在、登出后看不到。
```

你会看到：AI列出文件清单和页面清单，等你确认。确认后它会改文件，最后告诉你怎么本地运行。

本地运行后，你会看到注册页面。用你自己注册Supabase时的那个邮箱注册。

重要的一个坑：Supabase内置的邮件服务只能发给你项目所属团队成员的邮箱，频率目前是每小时2封（官方文档，2026年11月，数值可能变）。所以测试时用你自己的邮箱，不要一上来拿朋友的邮箱试，也不要连着点很多次「发送」。要让任意用户都能收到确认邮件，需要配置自定义SMTP，这是上线前要做的事，现在先不管，第8步会回来做。

如果看到别的：

- 点注册后提示`Email address not authorized`，就是上面这个限制，换成团队成员邮箱。
- 页面空白或控制台报错，见[页面白屏](/fix/blank-page)；报跨域见[CORS报错](/fix/cors-blocked)。
- 提示网络请求失败，见[fetch failed](/fix/fetch-failed)，同时回头看第0步，可能是网络对Supabase不友好。
- 一直读不到数据，也没有报错，多半是RLS策略没匹配上，见[RLS拦住了请求](/fix/supabase-rls)。

### 第7步：用两个账号验证RLS

这一步不能省。功能能用，不代表安全。

做法：在一个普通窗口用邮箱A登录，写两条笔记；打开一个无痕窗口，用邮箱B注册登录。B应该看到一条笔记都没有，B写的笔记A也看不到。

邮箱B的确认邮件会遇到上一步说的限制，所以B最好也是你团队成员的邮箱，比如你自己的另一个邮箱加进团队。具体怎么邀请成员，以Supabase后台的组织设置为准。

你会看到：两个账号各自只有自己的笔记。

如果看到别的：B能看到A的笔记，立刻停止上线，回到第5步，把现象告诉AI，让它逐条检查策略。这就是没配好RLS的症状，也是真实世界里最常见的数据泄露方式。

### 第8步：上线前的配置

本地能跑，上线还要三件事：

1. 在Vercel项目的环境变量里，把`.env.local`里那两个值再填一遍。Vercel添加变量时有「Config」和「Secret」两种类型，Secret保存后只写不读（官方文档，2026年11月）。这两个值是公开用的，选Config即可，将来的secret key一律选Secret。改了环境变量只对新的部署生效，所以填完要重新部署。线上读不到变量见[环境变量线上缺失](/fix/env-missing-in-production)。
2. 在Supabase后台的Auth设置里，把你的线上网址配进去（常见做法是配置站点地址和允许跳转的地址，具体名称以界面为准）。不配的话，邮件里的确认链接可能跳回localhost。
3. 配置自定义SMTP。内置邮件服务只给项目团队成员发信，别的邮箱会报`Email address not authorized`，还限制每小时2封（官方文档supabase.com/docs/guides/auth/auth-smtp，2026年11月）。不配的话，真实用户注册收不到确认邮件。做法：选一个邮件服务（比如Resend，见[Resend官方价格页](https://resend.com/pricing)），在Supabase后台Authentication的SMTP设置里填它给你的服务器地址、端口、用户名和密码，具体界面以Supabase官方文档为准。让AI带你一步步做也可以，把SMTP密码当作密钥，不要贴进对话。

```prompt 复制给Claude Code或TRAE
我要把这个项目部署到Vercel。请做上线前检查并列出清单，不要自动推送：
1. 全项目搜索：有没有硬编码的密钥、sb_secret_、service_role、数据库密码；检查git历史里是否出现过。
2. 列出线上需要配置的全部环境变量名（只要名字，不要值）。
3. 列出我需要去Supabase后台手动设置的项，尤其是线上网址和自定义SMTP（因为内置邮件只发给团队成员），并写明为什么。
4. 告诉我部署后怎么验证：注册、登录、写笔记、刷新、登出、换手机再登录。
```

你会看到：一份清单，第一项显示没有发现泄露。

确认没问题后，你自己用`git push`推送，等Vercel部署完成，用手机4G访问线上网址，走一遍注册登录。

如果看到别的：部署成功但登录失败，先看是不是环境变量没填或没重新部署；国内网络打不开，见[Vercel在国内打不开](/fix/vercel-blocked-in-china)。

## 验收：怎么知道真的成了

- 用邮箱A在手机上注册登录，写一条笔记；换电脑登录同一个账号，笔记还在。
- 邮箱B登录后看不到A的笔记，A也看不到B的。
- 在浏览器里查看页面源代码和网络请求，搜不到`sb_secret_`、`service_role`这些字样。
- 用一个不是团队成员的邮箱，在线上网址注册，能收到确认邮件（说明SMTP配好了）。
- `.env.local`没有出现在GitHub仓库里。
- Supabase后台Table Editor里每张表都显示启用了RLS。
- 你能说出「publishable key为什么能公开，secret key为什么不能」。

## 最常卡在这几个地方

- 线上能用、本地不行，或者反过来：多半是环境变量，见[环境变量线上缺失](/fix/env-missing-in-production)。
- 读不到数据、写不进去：RLS或权限授予的问题，见[RLS拦住了请求](/fix/supabase-rls)。
- 不小心把密钥推到了GitHub：立刻去后台停用并重新生成，再处理代码，见[密钥泄露急救](/fix/secret-leaked)。
- 请求失败、超时：见[fetch failed](/fix/fetch-failed)，并检查网络对Supabase是否友好。
- 浏览器控制台报跨域：见[CORS报错](/fix/cors-blocked)。

## 这一关的提示词合集

localStorage方案（只要本地存储时用）：

```prompt 复制给Claude Code或TRAE
我的网页需要把用户输入的数据保存在浏览器里，刷新页面后还在。请用localStorage实现。
要求：
1. 先用三句话告诉我你打算存什么、用什么名字存、数据长什么样，等我说「继续」再动手。
2. 读取数据时要处理「没有数据」和「数据坏了」两种情况，不能让页面白屏。
3. 加一个「导出备份」和「导入备份」按钮，数据以JSON文件的形式导出，因为localStorage清理浏览器就没了。
4. 完成后，教我怎么在浏览器的开发者工具里看到存进去的数据，并告诉我这些数据换一个浏览器为什么看不到。
```

确认项目形态：

```prompt 复制给Claude Code或TRAE
请先阅读当前项目，告诉我：

3. 如果要迁移，列出会改动哪些文件，原来的功能和样式怎么保证不丢。
只做分析，不要改任何文件。我选定方案后你再动手。
```

配置准备：

```prompt 复制给Claude Code或TRAE
我要把Supabase接到这个项目里。先不要写业务代码，只做配置准备：
1. 创建.env.local文件，里面放两个变量：NEXT_PUBLIC_SUPABASE_URL和NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY，值先留空，我自己填。
2. 检查.gitignore，确认.env.local被忽略；如果没有，加上。然后运行`git status`，证明.env.local不会被提交。
3. 同时创建一个.env.example，只写变量名不写值，方便以后看。
4. 安装官方包@supabase/supabase-js和@supabase/ssr。安装前先去Supabase官方文档（supabase.com/docs里Next.js的快速入门）确认当前推荐的写法。
完成后停下来，告诉我下一步我该做什么。注意：不要让我把任何密钥贴到对话里。
```

建表和RLS：

```prompt 复制给Claude Code或TRAE
请为「笔记」功能设计Supabase数据库，先只写方案，不要执行。
上下文：每个登录用户可以创建、查看、修改、删除自己的笔记，看不到别人的。
请给出：
1. notes表的字段（id、user_id指向登录用户、内容、创建时间），说明每个字段为什么要有。
2. 一份可以直接粘贴到Supabase后台SQL Editor里运行的SQL：建表、开启RLS、给authenticated角色授予必要权限、为select/insert/update/delete各写一条策略，条件是登录用户的id等于user_id（用auth.uid()）。查Supabase官方RLS文档确认写法，并建议用(select auth.uid())的形式。
3. 逐条解释这份SQL做了什么，让一个不会写SQL的人也能看懂。
4. 明确告诉我：这份SQL有没有可能让未登录的人读到数据。
验收标准：每张表都必须开RLS，没有任何策略是「允许所有人」。
```

登录和读写：

```prompt 复制给Claude Code或TRAE
请在这个Next.js项目里实现：邮箱+密码注册登录，登录后可以增加、查看、删除自己的笔记。
先说计划，等我确认再动手。计划要包含：要新建或修改哪些文件、登录状态怎么保存、页面有哪几个。
约束：
1. 只使用环境变量里的NEXT_PUBLIC_SUPABASE_URL和NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY。不要使用、不要提及secret key，前端代码里不允许出现任何以sb_secret_开头或叫service_role的内容。
2. 按Supabase官方Next.js文档的推荐方式处理登录状态。
3. 所有读写都通过supabase-js，并依赖RLS做权限，不要自己在前端「过滤掉别人的数据」当作安全措施。
4. 界面保持现有风格，注册、登录、登出、笔记列表各一个清楚的状态：加载中、失败、成功。
验收标准：我能注册、登录、写一条笔记、刷新后还在、登出后看不到。
```

