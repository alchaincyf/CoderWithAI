```error
（没有固定报错。典型的AI回复长这样：）
"我发现问题了，让我再修改一下……"
"抱歉，之前的修复没有生效，让我换一种方式……"
"现在应该可以了，请刷新试试。"（刷新后问题还在）
```

## 人话：这是怎么回事

这不代表你的需求太难，也不代表AI不行。常见原因有几个：它在**猜**，而不是看到真正的错误；每次修都在上一次的修补上再叠一层，代码越改越乱；对话太长，它忘了前面试过什么；或者问题的根子不在它修的那个地方。

这时候继续说「还是不对」，只会让它继续猜。该换打法的是你。下面按顺序来，不用全做。

## 最快的解法：把这段发给AI

先喊停，再换成这个提示（最好在退回干净状态之后）：

```prompt 复制给 Claude Code
停。先不要再改任何代码。我们已经在同一个问题上来回试了好几轮没解决。

请这样做：
1. 用三句话说明：现在期望的行为是什么、实际发生了什么、你已经试过哪些办法（以及为什么没用）。
2. 不要再猜。告诉我需要看到什么证据才能确定原因（浏览器控制台报错、终端日志、某个变量的实际值、网络请求的返回），并加上临时的日志输出，让我运行后把结果贴给你。
3. 根据证据给出根本原因，再说明最小的修改方案。如果有两种以上办法，列出来让我选。
4. 修改之前先告诉我会动哪些文件。
```

## 想自己动手的话

1. **停下，退回到最后一个好的状态。** 越修越乱的时候，最干净的做法是回退，而不是在乱的基础上继续。方法见 [undo-ai-changes](/fix/undo-ai-changes)。有 [Git](/words/git) 提交过的话最省事。
2. **给证据，不给感受。** 「还是不对」换成：控制台的红色报错原文、终端输出、截图。浏览器里按F12打开 [开发者工具](/words/devtools) 看 Console 和 Network，终端里看 [日志](/words/log)。
3. **先诊断，后动手。** 用 [计划模式](/words/plan-mode) 让AI先说原因和方案，你确认再改。
4. **缩小问题。** 让它在一个最小的页面或一个函数里复现问题，比在整个项目里改容易得多。
5. **开新对话。** 对话太长AI会糊涂。让它把「现状、已试过的方法、关键文件」总结出来，开新对话继续，见 [context-full](/fix/context-full)。
6. **换个角度问。** 让它解释这段代码在做什么，或者让另一个AI/模型独立看一遍。
7. **怀疑需求本身。** 有时是两个要求互相矛盾，让AI复述一遍你的需求，看它理解对了没有。

> [!warn] 小心AI用「绕过去」的方式让问题消失：删掉报错的检查、把测试改成必然通过、用try-catch吞掉错误。看到这类改动，要求它说明根因，并还原。

## 下次怎么避免

每个能用的状态都 `commit` 一次，随时可退。一次只改一件事，改完马上验证。提需求时带上验收标准：「做到什么算完成」。

## 还不行？

把问题缩到最小，附上报错原文和相关代码，到有经验的人那里求助，或者用别的模型再问一次。报错原文本身通常能在本栏目里搜到对应的急救条目。
