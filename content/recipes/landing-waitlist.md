## 你会做出什么

一个产品预热页：一句话说清你要做什么，三个卖点，一个输入框「留下邮箱，上线通知你」。访客提交后，邮箱被存进你的Supabase数据库，你在后台表格里能看到谁在什么时候留的，也能导出成CSV。

它是验证需求的最小办法：产品还没做出来，先看有没有人愿意留邮箱。留下邮箱的人，是你第一批用户。

页面本身是静态的，数据库只用来存邮箱，没有登录，没有后台界面（你直接用Supabase自带的表格看）。

## 开始前准备

- 会用AI做网页并上线，见 [第2关](/start/first-page)、[第3关](/start/go-live)。
- 懂一点数据库是什么，以及密钥怎么保管，见 [第4关](/start/save-data)。
- 一个 [Supabase](/words/supabase)账号。截至2026年11月，官方定价页写明免费计划可建2个活跃项目，数据库500MB，并且免费项目一周不活跃会被暂停。数字以官方页面为准。暂停的项目需要手动恢复，对等候名单这类低频项目，记得隔段时间进去看一眼。
- 国内读者注意：Supabase是海外服务，国内网络访问可能不稳，上线后务必用国内手机网络实测提交。若不稳，可考虑把后端换成国内的云数据库，思路相同，但要换实现。
- 想清楚你要对访客说的话：产品是什么、给谁用、为什么现在留邮箱有价值。

> [!warn] Vercel的Hobby免费套餐面向个人、非商业使用。如果你的落地页是在为一个商业产品做推广，请先阅读Vercel的条款，决定是否需要付费套餐，或换别的托管方式。

## 第1步：先做落地页本身

```prompt 复制给AI
我是不会写代码的人，要为一个产品做预热落地页，目标是让访客留下邮箱。

产品信息：
- 名称：
- 一句话介绍（谁用、解决什么问题）：
- 3个卖点（每个一句话）：
- 上线时间预期（可写「预计2026年Q1」）：

请先用5行以内说明计划，有拿不准的先问我，没有就直接做。

要求：
1. 单个 index.html，样式和脚本写在里面，不用框架，不依赖外部网络资源（字体用系统字体）。
2. 结构：首屏（大标题、副标题、邮箱输入框 + 「加入等候名单」按钮）→ 三个卖点 → 一个常见问题（3条）→ 页脚（版权、联系邮箱）。
3. 首屏必须在手机一屏内看到标题和邮箱输入框。
4. 风格：克制、专业，一个主色，大量留白。不要虚假的「已有 xxxx 人加入」之类数字，我们没有。
5. 表单暂时只做前端：邮箱格式检查，格式不对就提示，格式对就显示「提交成功」（先不连数据库）。
6. 每处我没提供的信息，用「【待补充】」标记，不要编造功能、数据或客户评价。

验收：手机和电脑宽度下均无横向滚动；邮箱框填错能提示；回车键也能提交；无控制台报错。做完请自己打开验证，如实报告。
```

你会看到：一个完整的落地页，点按钮会提示成功，但还没有真的保存。

## 第2步：建好数据库表，并设置安全规则

在Supabase新建项目后，让AI带你建表。这一步最关键的是「行级安全」（RLS，见 [supabase-rls](/fix/supabase-rls)）：我们要的规则是「任何人都能写入，但谁也不能通过网页读取」，否则任何访客都能把你的名单拉走。

```prompt 复制给AI
我在 Supabase 上新建了项目。请帮我设计并给出建表的 SQL，我会粘贴到 Supabase 的 SQL Editor 里运行。

需求：
1. 表 waitlist：id（自增主键）、email（文本，必填）、source（文本，可空，记录来源，如 twitter）、created_at（带时区时间，默认现在）。
2. email 不允许重复，且不区分大小写（用小写唯一索引）；给 email 加长度限制（不超过254）。
3. 开启行级安全。只添加一条策略：允许匿名用户（anon）INSERT；不要添加任何 SELECT、UPDATE、DELETE 策略，这样前端读不到名单。
4. 请逐行用大白话解释这段 SQL，并告诉我如何在 Supabase 后台确认 RLS 已启用。
5. 告诉我在 Supabase 后台哪里找到项目 URL 和可公开使用的 API Key（界面上可能叫 publishable key 或 anon key），并解释为什么这个 key 可以放在前端而 service_role 密钥绝对不能。
```

你会看到：SQL运行成功；在Table Editor里看到 `waitlist` 表，旁边有RLS已启用的标识。

> [!warn] 可以放前端的是publishable/anon key，它的权限完全由你的RLS规则限制。`service_role` 密钥能绕过所有规则，一旦放进网页或上传到GitHub，就是 [secret-leaked](/fix/secret-leaked)。

## 第3步：把表单接到数据库

```prompt 复制给AI
请把落地页表单接到 Supabase。我的项目 URL 是（填写），可公开 key 是（填写）。

要求：
1. 不使用npm和构建工具。可以直接用 fetch 调用 Supabase 的 REST 接口（POST 到 /rest/v1/waitlist），请求头带上 apikey 和 Authorization，并按官方文档确认请求格式，不要凭记忆写。
2. URL 和 key 放在文件顶部的常量里，并注明「这个 key 是公开的，没问题；绝不能放 service_role」。
3. 提交时按钮变「提交中…」并禁用，防止重复点击。
4. 成功：显示「已收到，上线第一时间通知你」。邮箱已存在（唯一约束冲突）：也显示成功提示，但不泄露「这个邮箱已注册」的信息。网络失败：显示「网络不太好，请稍后再试」，并保留输入内容。
5. 加一个隐藏的蜜罐字段（真人看不到，机器人会填），填了就假装成功但不提交。
6. 页脚加一句隐私说明：「仅用于通知产品上线，不会转卖，可随时联系 xxx 删除」，邮箱占位。
做完用真实提交测试一次，并告诉我如何在 Supabase 的 Table Editor 里确认记录；再测试：重复邮箱、格式错误邮箱、断网。
```

你会看到：提交后，Supabase的 `waitlist` 表里多了一行。

如果不对：

- 返回401或403：key填错，或RLS策略没建对，见 [api-401](/fix/api-401)、[supabase-rls](/fix/supabase-rls)。
- 浏览器控制台出现CORS报错：见 [cors-blocked](/fix/cors-blocked)，把完整报错发给AI。
- 提交一直转圈：见 [fetch-failed](/fix/fetch-failed)，也可能是国内网络访问Supabase不稳。

## 第4步：上线并实测

按 [第3关](/start/go-live)部署。上线后：用手机（关Wi-Fi）提交一个自己的邮箱，到Supabase表里确认。再用另一个邮箱提交一次。最后在页面里按F12，尝试在控制台用同一个key去「读」waitlist表，应该读不到，这证明你的RLS是对的。

```prompt 复制给AI
请帮我做一次安全自查：1. 项目里有没有 service_role 密钥或任何不该公开的内容（包括 Git 历史）；2. 用匿名 key 读取 waitlist 表是否被拒绝（请写一个测试命令，并告诉我预期结果）；3. 页面里有无编造的数据。逐项回答。
```

## 怎么验收

- 手机用移动数据提交，Supabase后台能看到这一行。
- 同一邮箱提交两次，表中只有一行。
- 匿名key读不到名单。
- 隐私说明已写，且邮箱联系方式是真的。
- 你能在Supabase的表格里导出CSV（界面上的导出入口，名称以实际为准）。

## 可以继续加的功能

- 来源统计：「读取网址里的 ?source= 参数写入source列，我就能知道哪个渠道带来多少邮箱。」
- 确认邮件：发邮件需要接邮件服务（如Resend）和域名，也要考虑发件限额与合规，先让AI调研：「我想在有人留邮箱后自动发一封欢迎邮件，请比较方案并告诉我免费额度的限制。」
- 访问统计：「帮我接一个不用Cookie的统计服务，先比较再动手。」
- 邀请机制：「提交成功后给一个专属分享链接，邀请好友能让我看到邀请数。」需要读取数据，要重新设计权限，务必让AI先讲方案。
- 收款预热：到了真正收费的阶段，见 [第7关](/start/get-paid)。

## 常见坑

- RLS没开：任何人都能读写你的表。
- 把service_role密钥写进页面。
- 试图在前端显示「已有N人加入」：那需要匿名可读，会暴露名单。要做就让AI做一个只返回数量的函数，不要开放表读取。
- 免费项目一周不活跃被暂停，表单随之失效。长时间无人访问的预热页，要定期检查。
- 收集邮箱就是收集个人信息，要写清用途，也要能响应删除请求。
